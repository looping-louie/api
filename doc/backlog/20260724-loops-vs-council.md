Implement the `/api/v1/loops` REST resource in the FastAPI API.

## Scope

Implement loop definition, persistence, status management, and changelog tracking.

Do not implement:

* Loop execution.
* Runs.
* Pipelines.
* Scheduling.
* Human review.
* Token counting.
* Timeout enforcement.
* Generic workflow engines.

Follow the existing project architecture, persistence patterns, authentication system, error envelope, naming conventions, and API versioning.

## Endpoints

Implement:

```text
GET    /api/v1/loops
POST   /api/v1/loops
GET    /api/v1/loops/{loop_id}
PATCH  /api/v1/loops/{loop_id}
DELETE /api/v1/loops/{loop_id}

GET    /api/v1/loops/{loop_id}/changelog
```

Use `PATCH`, not `PUT`, for updates.

## Loop model

A loop must contain:

```json
{
  "id": "uuid",
  "title": "Idea shaping",
  "description": "Transform a rough idea into a structured product proposal.",
  "flow": "roundtable",
  "status": "active",
  "stop_conditions": {
    "max_iterations": 3,
    "max_tokens": 50000,
    "timeout_seconds": 900
  },
  "agents": [],
  "output_contract": {
    "type": "files",
    "description": "Produce a structured product proposal.",
    "files": ["idea.md"],
    "schema": null
  },
  "created_at": "datetime",
  "created_by": "user-id",
  "updated_at": "datetime",
  "updated_by": "user-id"
}
```

The API must generate and manage:

* `id`
* `status`
* `created_at`
* `created_by`
* `updated_at`
* `updated_by`

These fields must not be accepted from the request body during creation.

## Flows

Support exactly these flows:

```text
direct
refinement
roundtable
```

Their meaning is:

* `direct`: each configured agent acts once without iterative feedback.
* `refinement`: a generator produces an output, reviewers evaluate it, and the generator improves it until approval or a stop condition is reached.
* `roundtable`: agents contribute during several rounds and an aggregator produces the final output.

The API only stores and validates the flow.

Execution behaviour is outside the scope of this task.

## Agents

Each loop agent must contain:

```json
{
  "id": "uuid",
  "model_id": "model-id",
  "persona_id": "persona-id",
  "role": "generator"
}
```

Support exactly these roles:

```text
generator
reviewer
aggregator
```

Rules:

* `model_id` is required.
* `persona_id` is required.
* `role` is required.
* Skills must not be included in loop agents.
* Do not add `skill_ids` or any equivalent field.
* The same model or persona may be reused by multiple agents.
* Agent IDs must be generated by the API when not supplied.
* Do not verify whether referenced models or personas exist unless the project already has a simple established mechanism for doing so.

## Flow validation

### `direct`

* Requires at least one agent.
* May contain generators, reviewers, or an aggregator.
* May contain at most one aggregator.

### `refinement`

* Requires exactly one generator.
* Requires at least one reviewer.
* May contain at most one aggregator.

### `roundtable`

* Requires at least two generator agents.
* Requires exactly one aggregator.
* Reviewers are optional.

Return the existing validation error envelope when these rules are violated.

## Stop conditions

`stop_conditions` must support:

```json
{
  "max_iterations": 3,
  "max_tokens": 50000,
  "timeout_seconds": 900
}
```

Rules:

* Every field is optional.
* Every supplied value must be a positive integer.
* At least one stop condition must be configured.
* Do not implement enforcement yet.

## Output contract

Keep the output contract small and generic:

```json
{
  "type": "text",
  "description": "Human-readable final answer.",
  "files": [],
  "schema": null
}
```

Supported types:

```text
text
json
files
```

Rules:

* `description` is required.
* `files` is optional and defaults to an empty list.
* `schema` is an optional arbitrary JSON object.
* `files` must contain at least one path when `type` is `files`.
* `schema` must be present when `type` is `json`.

Do not introduce description presets such as:

```text
shape_idea
plan_development
implement_tasks
```

These use cases must be expressible through `description`, `agents`, `flow`, and
`output_contract`.

## Loop status

Support exactly these statuses:

```text
active
disabled
archived
```

New loops must default to:

```text
active
```

Status changes must be performed through `PATCH /api/v1/loops/{loop_id}`.

Examples:

```json
{
  "status": "disabled"
}
```

```json
{
  "status": "active"
}
```

```json
{
  "status": "archived"
}
```

Rules:

* An active loop may become disabled or archived.
* A disabled loop may become active or archived.
* An archived loop cannot be modified but can be reactivated.
* Repeating the current status must be rejected as an empty effective change.
* Status transitions must create changelog entries.

Do not implement execution restrictions based on status yet.

## Changelog

Every loop must have an immutable changelog.

Use naming based on `changelog`, not `events`.

Suggested persistence model:

```text
loop_changelog_entries
- id
- loop_id
- change_type
- actor_id
- changed_at
- diff
- content
```

Supported change types:

```text
created
updated
enabled
disabled
archived
deleted
```

Each entry must contain:

```json
{
  "id": "uuid",
  "loop_id": "loop-uuid",
  "change_type": "updated",
  "actor_id": "user-id",
  "changed_at": "datetime",
  "diff": {
    "title": {
      "from": "Old title",
      "to": "New title"
    }
  },
  "content": null
}
```

### Creation entry

Creating a loop must generate a `created` entry.

The entry must store the complete initial loop representation in `content`:

```json
{
  "change_type": "created",
  "diff": null,
  "content": {
    "title": "Idea shaping",
    "description": "Transform a rough idea...",
    "flow": "roundtable"
  }
}
```

### Update entry

Normal updates must generate an `updated` entry.

The entry must contain only changed fields in `diff`.

Use this shape:

```json
{
  "description": {
    "from": "Previous description",
    "to": "New description"
  }
}
```

Do not store a complete snapshot for every update.

### Status entries

Status transitions must use specific change types:

```text
active -> disabled   = disabled
disabled -> active   = enabled
active -> archived   = archived
disabled -> archived = archived
```

The status change must also appear in `diff`:

```json
{
  "status": {
    "from": "active",
    "to": "disabled"
  }
}
```

### Deletion entry

Before permanently deleting a loop, create a `deleted` changelog entry.

Store the final loop representation in `content`.

Changelog entries must remain available after the loop itself has been deleted.

Do not configure cascading deletion from loops to changelog entries.

## Changelog actor

Obtain `actor_id` from the authenticated user.

Never accept `actor_id`, `created_by`, or `updated_by` from the request body.

If the current test infrastructure does not yet provide authentication, use the
existing test-user mechanism or dependency override used elsewhere in the API.

Do not invent a second authentication mechanism.

## Changelog endpoint

Implement:

```text
GET /api/v1/loops/{loop_id}/changelog
```

It must:

* Return entries ordered from newest to oldest.
* Follow the existing API pagination convention.
* Return the actor, timestamp, change type, diff, and content.
* Continue working when the loop has been deleted, provided changelog entries exist.
* Return the existing not-found error when neither the loop nor any changelog entries exist.

Do not implement changelog filtering or searching.

## Transaction requirements

The loop mutation and its changelog entry must be written in the same database transaction.

This applies to:

* Creation.
* Updates.
* Status changes.
* Deletion.

A loop change must never succeed without its corresponding changelog entry.

A changelog entry must never be created if the loop mutation fails.

## Listing

`GET /api/v1/loops` must follow the existing pagination convention used by the API.

Do not add filtering, searching, sorting, or cursor pagination unless already
required by shared project infrastructure.

Deleted loops must not appear.

Archived and disabled loops may appear in the normal listing.

## PATCH behaviour

`PATCH /api/v1/loops/{loop_id}` must:

* Update only supplied fields.
* Preserve omitted fields.
* Reject immutable fields.
* Revalidate the complete resulting loop.
* Update `updated_at`.
* Update `updated_by`.
* Generate the correct changelog entry.
* Reject an empty request.
* Reject a request that produces no effective changes.
* Reject modifications to archived loops.

Immutable fields include:

```text
id
created_at
created_by
updated_at
updated_by
```

Agent lists may be replaced as a complete field when supplied.

Partial editing of an individual agent is outside the scope of this task.

## Deletion

`DELETE /api/v1/loops/{loop_id}` must permanently delete the loop definition.

Before deletion:

* Create a `deleted` changelog entry.
* Store the final loop representation in the entry's `content`.
* Retain all previous changelog entries.

Do not cascade into runs or pipelines because those resources are outside this
task.

Return the existing not-found error envelope when the loop does not exist.
